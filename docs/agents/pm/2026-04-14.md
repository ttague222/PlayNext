## PRD Compliance

### User Flow
- **Implemented:** All required screens present — TimeSelect, MoodSelect, OptionalFilters, Results. Required inputs (time, mood) enforced. Optional inputs (platform, play style, session type, discovery toggle) all implemented. Fallback message surfaced in UI when filters are relaxed.
- **Missing:** "I'll play this" acceptance flow navigates back correctly, but there is no explicit "exit session" action — PRD §4.4 lists this as an explicit user action. Users can only start over, not cleanly exit with no choice.
- **Mismatch:** The Discovery Toggle behavior for anonymous vs. history-aware users (PRD §4.2 table) is partially collapsed — both paths hit the same surprise boost logic regardless of whether the user has signal history.

### Recommendation Engine
- **Implemented:** Full filter pipeline (time, mood, genre, platform, session type), heuristic scoring matching PRD weights, fallback hierarchy (relax platform → relax play style → relax time → partial match), surprise mode with indie boost and AAA penalty, franchise diversity enforcement.
- **Missing:** Fallback explanation text is less specific than the PRD example ("No exact matches for 15-minute competitive handheld games..."). Current messages are generic ("Showing games across all platforms").
- **Mismatch:** Scoring adds `random.uniform(0, 0.3)` noise — not in the PRD spec, though reasonable for variety. PRD §10 requires "deterministic, reproducible logic" for testability; this breaks that requirement.

### Game Catalog
- **Implemented:** Schema fully matches PRD §7 with correct required/optional fields, plus extended fields (`store_links`, `fun_fact`, `franchise`).
- **Missing:** Catalog size unknown from code alone. PRD targets 200–300 games for MVP. No tooling to audit count exists in the repo.
- **Note:** `subscription_services` field present and used in scoring.

### User Preference Signals
- **Implemented:** `worked`/`not_good_fit` feedback (post-accept), `played_loved`/`played_neutral`/`played_didnt_stick` via AlreadyPlayedModal, session tracking with reroll count, signal history stored in Firestore.
- **Missing:** Implicit signal data (reroll count, time-to-decision) is captured in sessions but **not fed back into scoring**. Preference learning (§8) is inert — signals are stored but don't influence future recommendations for the same user.
- **Mismatch:** `already_played` signal type is used in code but not defined in the PRD signal model (§8.5). Minor.

## Next 3 Priorities

### 1. Wire signal history into recommendation scoring
**Why:** The infrastructure exists (signals stored, `_get_recently_shown` queries history) but signals only deprioritize recently shown games — they don't boost games that `worked` or penalize `not_good_fit` for the same user. This is the core value loop of the product.
**Effort:** Medium

### 2. Audit and grow the game catalog
**Why:** Recommendation quality is directly proportional to catalog size. No tooling exists to know if the 200-game MVP target has been met. A simple admin endpoint or web-admin stats page showing catalog count + coverage by time/mood/platform would unblock informed curation.
**Effort:** Small

### 3. Improve fallback explanation specificity
**Why:** The PRD calls for transparent, context-specific fallback messages. Current messages ("Showing games across all platforms") don't tell the user what was relaxed or why. This is a low-lift fix with direct impact on decision confidence.
**Effort:** Small

## Growth Opportunities

1. **"Why Not?" for skipped games (Phase 2 spec):** The signal model already has a `skipped` type. Surfacing a "Why didn't you recommend X?" tap on the results screen would collect negative signals passively and surface the reasoning — directly reducing reroll frustration.

2. **Session completion rate dashboard:** The web-admin has an Analytics page but it's unclear what data it surfaces. Adding a visible funnel (sessions started → recommendations shown → accepted) would give a real-time signal on whether the core loop is working before launch metrics matter.

3. **Platform preferences persistence:** Users select platforms each session. Since Firebase Auth with anonymous sign-in is already wired, persisting the last-used platform preference locally (AsyncStorage) would reduce friction on repeat visits without requiring an account.

4. **Buckets as a Phase 2 engagement hook:** The bucket/save feature (already built, not in MVP PRD) is a strong retention mechanic — users building "Play Later" lists come back. Consider making this the primary post-accept CTA instead of just a secondary save icon on cards.

5. **Affiliate links as lightweight monetization signal:** `affiliateService.js` exists but isn't in the PRD or roadmap. Track click-through rates per game to understand purchase intent — this data could inform Phase 3 (Platform Integration) priorities.
